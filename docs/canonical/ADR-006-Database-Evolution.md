# ADR-006 — Database Evolution Rule (Dump Read-Only + Proposed Migrations)

## Status

ACEITO

## Contexto

A reconstrução da plataforma FCA/Midas SaaS parte de um dump legado congelado (`database/dump/Dump20260618.sql`) como **fonte de verdade do legado**, enquanto MDs/MAPs definem a **arquitetura desejada** e o SQL é a **materialização da evolução**.

O KILO Engine deve auditar continuamente Dump × MD × MAP × FRONT. Quando um objeto arquitetural definido nos MDs/MAPs **não existe no dump**, o comportamento anterior (ignorar ou criar direto no banco) está errado. Era necessária uma regra permanente de evolução de banco controlada.

## Decisão

O dump SQL congelado é **somente leitura**. Toda divergência entre Dump e MD/MAP gera um **relatório**, não uma mutação.

Quando um objeto arquitetural não existir no Dump:

- **Não ignorar** a ausência;
- **Não criar diretamente** no banco;
- **Gerar proposta SQL versionada** em `database/migrations/proposed/`;
- **Aguardar aprovação**;
- Somente objetos **aprovados** entram em `database/migrations/approved/`.

Objetos novos nascem de **MD/MAP**, nunca do frontend (ex.: nunca criar tabela porque um componente React existe).

SQL gerado pelo KILO recebe marcação obrigatória:

```sql
-- GENERATED BY KILO ENGINE
-- STATUS: PROPOSED
-- REQUIRE APPROVAL
```

## Consequências

- Evolução de banco passa a ser **controlada e rastreável**, não reconstrução desorganizada do legado.
- O dump permanece intacto como baseline de comparação.
- Propostas podem ser revisadas antes de virarem migrations oficiais.

## Alternativas Consideradas

- Criar tabela/SP diretamente ao detectar ausência: rejeitada (quebra controle e pode divergir da arquitetura).
- Ignorar ausência: rejeitada (perde-se a evolução necessária definida nos MDs).
